# 领导汇报机场排班流程图简化模式调研

> 调研日期：2026-08-17  
> 范围：面向管理层说明机场排班从输入到发布的运行机制；不替代 `spec.md` 中的业务规则、优先级或验收标准。  
> 证据原则：只采用 OMG 与 Microsoft/Visio 的一手规范、官方支持文档。

## 结论

领导汇报页应采用**横向跨职能流程图（swimlane / cross-functional flowchart）**，并使用一组受 BPMN 启发但不追求完整 BPMN 合规的简化符号：开始/结束、活动、判断、子流程、数据输入/输出。泳道按责任主体划分，阶段从左至右排列。这样一张图同时回答管理层最关心的三件事：谁负责、按什么顺序、异常在哪里被拦截。

不建议把求解器内部的候选筛选、迭代、权重或每条规则都展开到主图。它们应收进一个“生成并校验排班”的子流程，必要时由第二张技术附图解释。主图的目标是建立共同判断框架，不是复刻实现细节。

## 推荐图形结构

### 图类型

- **主图：横向跨职能流程图。** 3 条泳道以内，优先为“运行/排班人员”“排班系统”“主管或现场执行”。若责任主体本身不清晰，先以现有实际责任为准，不凭图形设计新增角色。
- **补图：规则校验或异常闭环图。** 只有当领导需要追问“为什么没有直接出表”时才展示；用一张单独的简化 BPMN 流程图说明输入校验、求解、无解/冲突和人工调整。

### 阅读顺序

固定为**左到右、上到下**：

1. 开始：导入或确认航班、人员、资质和锁定信息。
2. 输入校验：数据是否完整、是否存在无法满足的硬约束。
3. 生成：系统生成并校验候选排班（一个子流程）。
4. 复核判断：是否满足发布条件。
5. 成功路径：确认、发布、留痕，然后结束。
6. 异常路径：进入“补充数据/人工调整/重新生成”，只在明确重新进入的节点回流一次。

每个活动节点用“动词 + 业务对象”命名，例如“校验岗位与资质”“生成候选排班”“确认发布班表”；判断节点写可回答的问题，例如“数据完整吗？”、“满足发布条件吗？”。所有判断出边必须有短标签，如“是/否”或“通过/需处理”。

### 节点与符号控制

- 主图建议 **8--12 个流程节点**，含 2 个判断；超过 12 个时先合并同一责任、同一目的的连续动作，或下沉为子流程。
- 至多 **3 条泳道、4 个阶段栏、2 个判断节点**。这些是领导汇报的版面控制建议，不是 OMG/Microsoft 的规范上限。
- 核心图形限为 4 类：开始/结束、活动、判断、子流程；只有明确要说明导入或输出文件时再增加数据图形。此建议直接遵循 Microsoft 对“三或四种图形”的默认做法。
- 避免交叉线、长距离回线和并行的“是/否”分支。Microsoft 对大图建议使用 On-page/Off-page reference，而非难以追踪的长连接线。

### 异常怎样呈现

- **常规异常只在判断后的“否”分支出现一次。** 例如“数据完整吗？”否 -> “补充/修正输入” -> 回到“输入校验”；“满足发布条件吗？”否 -> “人工调整并记录原因” -> 回到“生成并校验”。
- **不要把异常与正常路径同权展开。** 主路径用实线和中性色；异常路径用橙色虚线或在节点左上角加警示标记，并配一行简短结果（如“退回补数”“转人工复核”）。颜色只能辅助，仍须依靠分支标签表达含义。
- **无法在当前页闭合的异常**用“异常处理子流程”或跨页引用承接；副图再列出冲突类型、责任人和恢复条件。这样符合 Microsoft 对子流程及跨页引用处理复杂流程的用途说明，也保持主图可读。
- **终止与可恢复异常分开。** 可恢复异常有唯一回流点；不能继续自动处理的情形进入“人工处置/待决”结束点，不画成隐含成功。

## 可直接交给制图人的版式

```text
准备                 生成与校验                   复核与发布
运行/排班人员  开始 -> 确认输入 ----> [补充/修正输入] -----------+
                         |                                      |
排班系统              校验完整性? --否---------------------------+
                         |是
                         v
                    [生成并校验排班] -> 满足发布条件? --否-> [人工调整并记录]
                                               |是                   |
主管/现场执行                                  v                    +-- 回到生成
                                           [确认并发布] -> 结束
```

制图时应把每个节点放进实际负责方的泳道；上图仅说明阅读次序，不表示项目现有规则或角色已经如此定义。具体节点、判断条件、回流是否允许，必须从当前 `spec.md` 与实际执行事实中确认后再落图。

## 不采用的模式

- **纯线性流程图**：无法清楚交代系统、排班人员和主管之间的交接责任。
- **完整 BPMN 编排图**：符号和边界事件过多，适合实施与审计设计，不适合首屏管理汇报。
- **把规则逐条画成分支树**：会将主图从运行路径变成规则目录，节点、回线和阅读负担快速失控。

## 证据边界

本报告中的“8--12 节点、3 条泳道、4 个阶段、2 个判断”是针对领导汇报可读性的设计建议，不是 OMG 或 Microsoft 的强制标准。已被一手资料直接支持的事实是：BPMN 提供事件、活动、网关和泳道等流程表达；跨职能流程图适合表达责任主体与阶段；基础流程图通常只使用三到四种形状，复杂步骤和大图可使用子流程及页内/跨页引用。
