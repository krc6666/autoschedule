# 当天排班求解性能调研

- 调研日期：2026-08-03
- 调研范围：HiGHS MIP 求解配置、字典序多目标、模型复用、MIP start，以及 Google OR-Tools 官方员工排班示例
- 资料范围：仅使用 HiGHS 官方文档/源码/示例、Google OR-Tools 官方文档/源码，以及本项目所用 `highs-ts` 包的上游源码

## 结论摘要

1. **当前“把当天全部岗位和合格人员一起求解”的方向是成熟做法，不是结构性错误。** Google OR-Tools 官方员工排班示例同样使用“人员 × 班次”的 0/1 变量、岗位覆盖约束、人员冲突约束和公平目标。本项目进一步只为真实合格的“人员-岗位”组合建变量，这种稀疏建模应保留。
2. **当前最明显的结构性性能风险位于求解器适配层。** 项目会为每一层排班优先级重新构造完整 `RawModel`，重新调用 `Highs_passMip`，再要求 HiGHS 精确求到最优；当天组合条件启用后，外层还可能再次构模并从发生变化的目标层继续求解。这个机制符合字典序规则，但会把一次排班放大成许多次完整 MIP 求解。
3. **HiGHS 已原生支持字典序多目标、修改目标系数、追加约束和设置完整/部分初始解。** 官方示例同时给出了“手工逐层求解并锁定前层结果”和“使用内置多目标”的方式。项目现在采用前一种，因此不是自创错误算法；问题在于当前 `highs-ts` WebAssembly 包没有暴露后一种所需的 C API，也没有暴露模型增量修改和 MIP start API。
4. **只增加少量航班就达到 30 秒，不应通过延长超时来掩盖。** 约 15 人、约 54 个岗位本身不是异常规模。应先记录每次模型的变量数、约束数、非零系数数、目标层数、外层重算轮数和每层耗时，再优化重复装模/求解。
5. **不建议立即换成 OR-Tools。** CP-SAT 很适合员工排班，但 Google 官方只提供 C++、Python、Java 和 C#/.NET 安装入口，没有官方浏览器 JavaScript 运行包。当前产品是纯浏览器、静态部署；直接替换会引入后端或非官方 WASM 依赖，并不能自动消除多目标重复求解问题。

以上第 2 点是代码审查确认的高风险结构，但在真实匿名输入的分层耗时数据完成前，不能把它写成唯一根因。

## 当前项目的实际结构

### 已采用的成熟做法

- `src/domain/kernel/daily-schedule-optimizer.ts` 只为通过资格筛选的人员-岗位组合建立 0/1 选择变量，并为每个岗位建立空缺变量。
- 同一岗位的人员选择与空缺满足一个完整性约束；同一人员的时间冲突、同航班并行限制和工时上限使用显式约束，而不是事后修补。
- 岗位完整性、值班、保护、公平和稳定顺序使用具名的字典序目标；前一目标固定后才优化下一目标，没有使用难以解释的超大综合权重。
- `src/infrastructure/solver/highs-solver.ts` 把同一次排班的剩余总时间传给 HiGHS 的 `time_limit`，并在到达总 deadline 后停止。
- `presolve` 没有被关闭，因而使用 HiGHS 默认的 `choose` 自动策略。
- `random_seed = 0` 与 HiGHS 默认值相同，结果可重复。

### 已确认的性能放大点

1. `HighsSolver.solveExclusive()` 遍历所有字典序目标。
2. 每个目标都会重新执行 `rawModel(...)`，其中复制全部变量、全部基础约束和此前目标锁定约束。
3. 每个目标都会调用一次 `highs.passModel(...)`。`highs-ts` 的实现会调用 `Highs_passMip`，把整个模型重新传入求解器。
4. 每个目标随后调用一次 `highs.solve()`，并设置 `mip_rel_gap = 0`，要求证明精确最优。
5. 当组合条件在第一次结果中被命中时，`optimizeDailySchedule()` 的外层 `while` 会重建问题并继续求解；`incrementalProblem()` 会保留前缀目标值，已经减少了一部分重复工作，但变化点之后仍要再次装模和求解。
6. 当天问题的目标数由输入决定。代码除了候选规则目标外，还会加入 4 个覆盖目标、值班目标、拆成多层的工时/疲劳目标，以及部分按岗位细分的稳定目标。因此一次“生成排班”不是只调用一次 MIP 求解。

这解释了为什么报错中最后出现的目标名不一定是制造慢问题的规则：它只表示 30 秒在执行到该层时耗尽，前面所有层消耗的时间同样需要统计。

### 关于字典序目标

HiGHS 官方多目标示例展示了两种正规实现：[S4]

1. 手工方式：求解第一目标，追加约束锁定第一目标值，再求第二目标；
2. 内置方式：添加多个 `HighsLinearObjective`，设置不同 `priority`，关闭混合目标后由 HiGHS 执行字典序优化。

项目现有方式与官方手工方式相同，所以不应改成单个超大权重目标。更成熟的优化方向是让同一模型常驻 HiGHS，由官方 API 管理多目标或增量修改，而不是改变现有业务优先级。

### 关于 MIP gap

将 `mip_rel_gap` 从 0 调回默认值可能更快，但会允许 HiGHS 在尚未证明精确最优时结束。项目随后会把当前目标值锁定给下一层，因而一次近似结果可能改变后续人员安排。除非 owner 明确接受“在极小差距内近似最优”，否则不能把放宽 gap 作为无行为变化的性能修复。

### 关于 MIP start / warm start

官方 C API 支持完整和部分初始解；这可用于把前一目标层、前一次组合迭代或重新排班前的可行班表交给求解器。[S3] 但 MIP start 只是帮助更快找到较好可行解，不替代证明每层最优。当前包装层没有相关导出，因此它应排在“复用模型/原生多目标”之后评估。

## OR-Tools 官方员工排班示例

Google 官方员工排班页面使用 CP-SAT，并采用以下模型：[S5]

- `shifts[(n, d, s)]` 是人员 `n` 在日期 `d` 是否承担班次 `s` 的布尔变量；
- 每个班次恰好由一人承担；
- 每人每天最多承担一个班次；
- 用总班次数的上下界使班次尽量均匀；
- 在有偏好时，用目标函数最大化满足的班次请求。

官方更完整的 `shift_scheduling_sat.py` 示例还包含：[S6]

- 固定安排；
- 连续班次数量的硬边界与软惩罚；
- 周期工作量上下界；
- 禁止或惩罚某些相邻班次转换；
- 每类班次的覆盖人数；
- 有限求解时间。

这些做法与本项目的业务结构可以这样对应：

| OR-Tools 示例          | 本项目对应做法                                     |
| ---------------------- | -------------------------------------------------- |
| 人员-日期-班次布尔变量 | 人员-当天岗位选择变量                              |
| 每班恰好一人           | 岗位选择一人或显式空缺                             |
| 每人每天最多一班       | 按真实航班时段建立冲突约束，并允许不重叠的多个任务 |
| 固定安排               | 值班或具体岗位锁定                                 |
| 班次转换限制           | 岗位衔接、恢复和连续轮岗规则                       |
| 覆盖需求               | 岗位完整性和空缺优先级                             |
| 均衡目标               | 工时、疲劳、频率和覆盖公平目标                     |

因此，**当前核心建模形态与成熟排班系统是一致的**。差别主要在于本项目的岗位比固定早/中/晚班更细，且必须保留明确的多层业务优先级。

CP-SAT 要求约束使用整数。[S9] 若未来迁移，需要把工时统一成分钟、把所有连续量离散化，并重做求解器适配、浏览器运行和语义等价验证。Google 官方安装页当前只列 C++、Python、Java 和 C#/.NET，没有 JavaScript/browser 版本。[S10] 因此它适合作为建模参考，不适合作为本轮直接替换项。

## 当前性能测试的缺口

当前性能测试已经覆盖：

- 15 人、32 个岗位的完整排班；
- 32 个岗位加 5000 条历史记录；
- 16/32 个岗位的少量 p50/p99 样本；
- 最多五人轮岗无解时的终止边界。

但它们还不能拦住本次问题：

1. 规模测试上限只有 32 个岗位，没有覆盖约 54 个岗位的当前业务量。
2. 夹具中的 15 人全部具备所有岗位资质，航班和岗位形态规则整齐，不能代表真实的稀缺资质、值班锁定、历史连续和末班恢复组合。
3. p50/p99 每项只有 2 个正式样本，且 16/32 岗位都允许接近 30 秒才失败；它更像“不得超过产品硬超时”，不是能提前发现退化的性能门槛。
4. 测试只记录整个排班或页面阶段耗时，没有记录每次 MIP 的变量、约束、非零系数、目标 ID、求解耗时和外层组合重算次数。
5. 5000 条历史记录测试可以保护历史预处理，但不能证明航班增加后模型求解仍稳定。

## 推荐的成熟技术路线

### 第一阶段：先建立可定位的真实性能基线

1. 将实际失败输入匿名化为约 15 人、约 54 岗位的固定测试夹具，不保存姓名或其他个人信息。
2. 在 `SolverPort` 边界记录变量数、约束数、非零系数数、实际目标层数、每层耗时、终止状态和外层组合重算轮数。
3. 连续运行至少 5 次，分别记录冷启动与 WASM 已加载后的耗时；使用中位数和最慢值，不用单次偶然结果定结论。
4. 把用户规模的硬失败门槛显著收紧到 30 秒以下；具体阈值应根据真实机器基线确定，避免在不同 CI 机器上制造随机失败。

### 第二阶段：按收益和风险排序

1. **优先消除没有有效系数或已由前层决定的无效目标。** 必须以目标值和最终班表语义等价测试证明，不通过综合权重合并层级。
2. **评估让模型在 HiGHS 内常驻。** 优先使用官方原生字典序多目标；若包装层暂不支持，再评估暴露官方 `changeColsCost`、`addRow` 等增量 API。实现应位于 `highs-ts`/基础设施边界，不侵入业务规则。
3. **在包装层有官方 API 后评估 MIP start。** 把上一层或上一轮的可行解作为启动解，同时仍完成当前层最优性证明。
4. **保留稀疏候选建模、HiGHS presolve 默认策略、统一 deadline 和 Worker 隔离。** 这些都是当前正确的结构。
5. **用现实夹具验证每一步。** 每次优化必须比较岗位、人员、空缺、工时、疲劳、锁定、说明和决策记录，确认业务结果不变。

### 明确不应采用

- 不把超时从 30 秒简单提高到 60 秒或更长。
- 不用超大权重把全部优先级塞入单目标；这会改变并隐藏规则顺序。
- 不在没有语义授权时放宽 `mip_rel_gap`，也不接受超时产生的部分方案。
- 不通过更换 `random_seed`、多次随机重试或挑最快结果掩盖模型问题。
- 不对当前无多线程支持的 WASM 盲设 `parallel=on`。
- 不为了“主流”直接换用非官方 OR-Tools JavaScript/WASM 包。
- 不继续用“全部人员具备全部资质”的简单夹具代表真实生产性能。
