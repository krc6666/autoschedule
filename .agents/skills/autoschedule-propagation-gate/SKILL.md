# autoschedule 多消费者传播门禁

本 Skill 不定义具体排班产品规则。它强制：多处会用到的知识只能有一个主人/编译点，改前填矩阵，少接一处不算完成。

## 何时必须使用

任务命中任一即整份执行本 Skill，不得跳过：

- 新增/修改业务硬规则或硬约束
- 新增/修改机制策略（重排让步、安全快照/守卫装配、补差分级等）
- 新增/修改持久化或边界字段（设置、迁移、页面编辑、localStorage、Excel 读/写、测试合同）
- owner 或上下文出现：漏接、唯一事实源、传播矩阵、第二套判断、影子状态、前后口径不一致

与 `autoschedule-rule-evolution` 同时命中时：先本 Skill 做传播矩阵与消费者清单，再按 rule-evolution 查阶段覆盖与冲突；冲突仍先停下来问 owner。

## 强制步骤（写文件前）

1. 用一句话标明本次属于哪一类（可多选）：业务硬规则 / 机制策略 / 持久化字段。
2. 指出唯一事实 owner 或唯一编译点；若还没有，先设计归属，禁止先在多处手抄。
3. 在根目录 `rule-propagation-matrix.md` **追加**本条矩阵（不要清空历史条目），至少列出：
   - 输入事实
   - 候选池 / 求解 / 补缺覆盖 / 恢复 / 轮岗公平 / 人工调整（不适用写原因）
   - 最终复核 / 守卫 / 凭证（机制策略尤其要写）
   - 保存 / 展示 / localStorage / Excel 读 / Excel 写 / 迁移（持久化尤其要写）
   - 测试（含反向或往返；不适用写原因）
4. 矩阵填完后才能改代码。交付时对照矩阵逐项勾选已接入。

## 完成标准

- 矩阵勾到的每一处都已接入；禁止只改主路径、漏确认/凭证/导出/测试。
- 业务硬规则：保留“合法结果被真实后置路径改坏必须拒绝/回退”的反向回归。
- 机制策略：所有同类调用方走同一编译结果；旧拼装方式不可用（类型或测试证明）。
- 持久化字段：默认值与往返一致；某边界不适用须在矩阵写明。
- 修漏接 bug 必须新增长期回归，断言用户可观察行为。

## 停止条件

出现第二套等价判断、职责归属不清、矩阵消费者无法列全、或必须放宽硬约束才能让测试绿：停止扩大修改，列出冲突与选项，等 owner 裁决。

## 不要做

- 不把本 Skill 条文复制回 AGENTS 成长文
- 不创建兼容转发、旧别名、长期双轨装配
- 不擅自 commit / push
