# autoschedule 历史顽疾与防复发手册

本文记录开发过程中反复出现的失败模式、真实根因、有效修法和最低回归要求。它不是当前产品规格；具体业务口径和优先级始终以根目录 `spec.md` 为准。

## 1. 使用方法

- 先用症状在下表找相似失败模式，再回到真实代码和数据验证，不把历史经验当成当前根因。
- 人名、航班号和岗位只用于说明旧事故，任何实现和测试都必须匿名并适用于所有合格人员。
- 旧问题已经修过不等于不会复发。新规则修改相同阶段时，必须重跑对应回归。
- 页面上写了规则、代码里有排序字段或排班后有交换函数，都不能证明规则真正生效；最终班表才是事实。

## 2. 最核心的历史教训

| 症状                                          | 真实根因                                                                          | 有效修法                                                                       | 必须保留的回归                                             |
| --------------------------------------------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------- |
| 新增规则后旧规则失效                          | `scheduler.ts` 同时承担资格、排序、锁定、补洞、轮岗和反馈，局部条件改变了全局顺序 | 拆分职责，用中央管线和中央规则合同显式排序                                     | 语义快照与高风险规则矩阵                                   |
| 某人长期固定在 G20 等岗位                     | 低频合格人员先被普通岗位占用，频率比较发生太晚；后置两人交换找不到链路            | 重点岗位在生成阶段提前处理，复核直接接替、同航班、重叠航班和最多三人链路       | 高频人员存在安全替代时不得继续固定                         |
| 规则页面显示“强保护”但结果仍突破              | UI 文案、规范和真实候选处理分别维护                                               | 规则页面从中央合同生成；反馈来自结构化决策和最终事实                           | 页面合同、执行顺序和反馈一致                               |
| 值班人员明明空闲却不能补 G10                  | 把“值班岗位锁定”扩大成“值班人员全天锁定”                                          | 最终班表保留12点前上午航班，只锁定晚撤 assignment ID，完成目标后允许补普通岗位 | 晚撤岗位不动、上午岗位可安全轮换且空闲值班人员可补普通岗位 |
| 分队长并行督导仍不能释放人手                  | 用分流提前撤岗后的个人时段判断航班是否重叠                                        | 重叠按航班原始保障时段判断，工时按完整督导时段并集计算                         | 分流不改变重叠事实，释放岗位后空缺减少                     |
| 点击排班报 `Maximum call stack size exceeded` | 递归补洞在岗位和人员之间循环传递空位，没有深度与访问状态边界                      | 限制重排人数、每步空位数量并记录访问状态                                       | 环形夹具必须终止且不栈溢出                                 |
| 行政支援模式岗位重复或消失                    | 把行政岗位理解成额外岗位，而不是同名替代                                          | 同航班同名行政岗位替换常规岗位；没有行政同名项时保留常规岗位                   | 开关前后岗位名称集合完整且不重复                           |
| 规则保存后当前班表看似已执行                  | 设置已更新，但现有 assignments 仍是旧结果                                         | 标记班表过期，暂停规则执行反馈，要求重新排班                                   | 保存不静默重排，重新排班后才生效                           |
| 反馈声称执行但实际人员已手调                  | 自动决策记录没有随人工调整失效                                                    | 清理被影响证据，从最终班表重新计算反馈                                         | 人工换人后旧说明消失                                       |
| 导出配置后再次导入仍要手填规则                | 新字段只加到页面或状态，遗漏 Excel 和迁移                                         | 完成状态、默认、迁移、导入、导出、页面和往返测试闭环                           | 配置导出再导入保持等价                                     |
| 浏览器页面卡死或排班过慢                      | 主线程执行组合搜索，或补洞搜索无界                                                | Web Worker、可见进度、搜索边界、真实规模性能回归                               | 切换模式和生成排班可终止且 UI 不冻结                       |
| 修改了错误项目副本                            | IDE 仍指向旧 C 盘目录，真实仓库已移动到 G 盘                                      | 每次先查 Git 根目录和进程命令行                                                | 最终报告真实绝对路径                                       |

## 3. 排班管线与优先级

### 弯路：只在候选排序里追加一个字段

`G20` 高频问题曾多次“已经有频率字段”却仍然发生。原因通常不是没有统计，而是：

1. 任务处理顺序先消耗了低频候选。
2. 稀缺资质预留把人保留给后续普通岗位。
3. 锁定或保护在频率比较前已经排除了替代人。
4. 后置复核只检查当前两个人，没检查可释放的第三人。
5. 最近 6 个工作日窗口看不到更长期的明显失衡。

解决时必须沿完整路径检查，不能看到 `positionFrequency` 字段就宣布已实现。

### 弯路：把所有规则一起算成一个分数

隐藏权重会让排班员无法知道为什么某人胜出，也无法保证新增规则不改变旧优先级。项目已经明确选择：

- 使用具名字段。
- 使用固定阶段。
- 使用逐项字典序比较。
- 只有前项相同时才进入下一项。
- 每次突破记录命中的前置规则。

不得用 `100000`、综合疲劳分或姓名偏置修补局部结果。

### 防复发动作

新增规则前必须写一张冲突表：

| 项目     | 必须回答                                          |
| -------- | ------------------------------------------------- |
| 规则 ID  | 唯一、稳定、用于结构化决策                        |
| 阶段     | 硬约束/特殊锁定/完整性/保护公平/稳定排序/后置复核 |
| 前后关系 | 明确排在谁前、谁后                                |
| 强度     | 不可突破/优先避开/无人替代时兜底                  |
| 锁定对象 | assignment、岗位组、人员或日期                    |
| 失败结果 | 留空、保持原人或允许突破                          |
| 反馈     | 写明证据和具体阻塞原因                            |

## 4. 岗位完整性与补洞

### 中间空洞

曾出现 `H05/H06` 空缺而 `H07/H08/H09` 有人的情况。岗位配置顺序不仅是展示顺序，也代表填充顺序。补洞时要验证：

- 同一航班后序普通柜台是否可安全前移。
- 前移是否满足目标岗位资质，而不是只看人员已在本航班。
- 督导兼任、引导复用和人工岗位不能被错误当作普通柜台移动。
- 前移后备注、岗位 ID、工时和疲劳仍对应目标岗位。

### 岗位完整性不能只看空缺数

“总空缺从 2 变 1”不代表方案合理。还要检查：

- 是否制造了新的源岗位空缺。
- 是否把早班空缺挪到了下午。
- 是否破坏 `KE166` 绑定组或值班锁定。
- 是否让一个人发生非法重叠。
- 是否把重点岗位连续问题转移给另一个人。

### 分队长并行督导

历史上有两个关键坑：

1. 分流岗位提前撤岗只改变个人实际结束时间，不改变两个航班原始保障时段的重叠事实。
2. 允许一名分队长同时督导两个短时重叠航班后，工时不能简单相加，必须按时段并集；疲劳仍分别累计。

搜索必须有边界：最多重排的人数、每步传递的空位数、同一链中人员与岗位去重、最终必须净减少空缺。

## 5. 锁定、兼任和特殊角色

### 锁岗位，不要锁人

值班、人工调整和特殊岗位最容易出现过度锁定。正确问题是“哪个 assignment 不能移动”，不是“这个人今天完全不能再参与”。

`FD573/G10` 的历史空缺就是典型例子：值班人员已有早班和晚撤，但下午空闲、有资质、不超工时；旧逻辑按 `currentDutyStaffId` 把他从所有补缺候选排除。修复后只保护具体值班岗位，普通空档继续参加候选比较。

每次新增锁定都要测试：

- 锁定岗位不会被直接接替、交换或三人链移动。
- 同一人员在其他不冲突时段仍可正常工作。
- 锁定身份不会污染不相关航班。

### `KE166` 机动督导

历史上曾把顶部督导与柜台强制绑定，导致空闲的合格督导进不了候选池，并反过来锁死柜台轮换。当前规则必须先排完柜台和重点岗位轮换，再安排顶部督导：

- 有不占用该时段柜台的合格人员时，顶部督导独立承担，不与柜台绑定。
- 只有没有独立人选、否则会出现岗位空缺时，才允许督导兼任规则范围内的柜台。
- 兼任发生后，两格作为一个明确岗位组，工时不重复、疲劳分别累计、轮岗时整组替换。
- 所有督导资质人员按同一规则参与，不设置姓名或分队长特例。
- 普通 `KE166` 常规岗位先参加同航班和重叠航班轮岗；兼任组形成后才作为特殊组保护。

### 引导复用

引导是从该航班自上而下最后一个符合条件的常规岗位人员复用，不应凭空再占用一名人员。展示时可以单独成行，但负荷和工时不能重复累计；人工输入或更换后必须重新校验并更新反馈。

### 行政支援

历史上“支援”与“行政支援”术语混淆，导致岗位类型和人员类型语义不清。维护时只使用当前 `spec.md` 定义，不复活旧分类。

行政支援模式要分别验证：

- 同名岗位替换，不是叠加。
- 没有行政同名岗位时保留常规岗位。
- 行政人员和行政岗位按当前规则排除工时、疲劳与历史统计。
- 开关变化使旧班表失效并重新生成。

## 6. 轮岗、公平与动态疲劳

### 重点岗位与普通岗位不是同一强度

历史需求逐步明确：一号、申报、督导、控制、送资料属于重点岗位；普通柜台仅低优先级防止第三次连续。不能把所有岗位都用相同频率规则，否则会牺牲完整性和重点岗位公平。

重点岗位至少检查：

- 上一工作班是否同一“航班号 + 岗位”重复。
- 当前自然月次数。
- 最近确认窗口内次数。
- 是否存在当天空闲的低频合格人员。
- 是否可在同航班、重叠航班或三人链中安全调整。

### 不要只做排班后两人交换

两人直接交换常因资质不对称失败。有效复核顺序通常是：

1. 空闲合格人员直接接替。
2. 同航班两人交换。
3. 所有时段重叠航班两人交换。
4. 包含被释放人员的三人开放重排。
5. 在同航班和目标时段重叠航班中，把已排人员也纳入候选，按两人、三人、四人、五人寻找参与人数最少的安全闭环或由空闲合格人员补齐末端岗位的开放式连续腾挪。

每一步仍需通过统一安全检查，不能复制一套较弱硬约束。

### 动态疲劳不是每天强行相等

owner 的宏观原则是跨工作班互补：今天累的人下个工作班尽量轻松，今天轻松的人可以承担较重任务。不要为了当天疲劳差好看而破坏稀缺岗位、重点岗位轮换或完整性。

末班重点岗位人员有更强恢复需求：

- 下个班优先避开重点岗位。
- 可配置时间之后尽量不再安排航班。
- 如果下午与晚上必须二选一，优先下午，让员工更早回家。
- “早上上班、下午长空档、晚上再回来”的防割裂规则只适用于受保护人员，不能扩展到全员。
- 下个班值班应尽量提前换人；无安全方案时保留完整性并反馈。

### 反馈必须说明无法轮换的真实原因

不能只写“规则未落实”。至少从下列原因中给出实际命中项：

- 没有其他目标岗位资质人员。
- 其他人员被值班、`KE166` 或人工岗位锁定。
- 时间冲突或夜班能力不足。
- 每日工时上限。
- 严格岗位衔接。
- 跨工作日恢复或疲劳保护。
- 交换会制造新空缺。
- 安全重排超过明确边界。

## 7. 业务事实、展示和反馈

### 隐藏不等于删除

曾因界面不显示 `H02` 的“一号”备注而丢失业务数据，导致重点岗位识别和恢复规则失效。展示层可以隐藏冗余文字，但模型、归档、导出和规则匹配必须保留原始备注。

### 反馈不能来自旧决定

自动排班后人工拖拽会让原 decision trace 失效。反馈必须基于最终 assignments 或仍有效的结构化决策；不得继续声称原规则已执行。

反馈保持简短但可核对：

- 日常摘要说结果。
- 规则反馈说是否执行及异常原因。
- 人员说明优先使用姓名、航班英文代码和重点岗位标签。
- 不重复堆完整航班号、时间、柜台号和疲劳点，除非这些是判断证据。

### 页面与算法不能维护两套规则

规则页应从中央合同生成。任何手写说明都可能随着实现变化而过期。新增规则时同时检查中央合同、页面、反馈、`spec.md` 和测试快照。

## 8. 配置、迁移和导入导出

### “页面能填写”不代表配置已经完成

规则参数新增后必须逐项检查：

1. 类型定义。
2. 默认状态。
3. localStorage 迁移与版本。
4. 配置页读写。
5. Excel 导出。
6. Excel 导入。
7. 旧文件缺列时的明确默认。
8. 导出再导入的往返测试。

历史上岗位类型默认值处理不当，曾让大量普通督导被默认成机动督导。迁移不能靠全局字符串替换，必须基于旧版本结构和业务条件。

### Excel 读取业务值，不依赖颜色

值班备勤模板可以保留视觉样式，但用户手工把“休”改成“备勤”后颜色不同不应影响导入。解析应以日期、姓名和单元格文本为准；颜色只用于导出展示。

### 工作表替换语义必须明确

- 工作表不存在：通常保留当前配置。
- 工作表存在但只有表头：按产品合同决定是否清空。
- 某行无效：指出表名、行号和原因，不静默吞掉。
- 一类规则失败：不要误覆盖其他已成功解析的配置。

## 9. 性能、递归和运行状态

### 组合搜索必须设计终止条件

补洞、轮岗和三人链很容易形成环。最低安全边界：

- 最大参与人数。
- 最大链路深度。
- 每步最多产生的空位数。
- 已访问状态签名。
- 同一人员和岗位在单链中不重复。
- 候选数量稳定排序。

性能测试不能只断言“不抛错”，还应设置真实规模和可接受时间边界。

### 主线程卡死

行政支援切换和生成排班曾因同步计算冻结页面。计算应进入 Worker 或至少提供不会阻塞交互的执行边界；右下角进度必须来自真实阶段，不用假动画。Worker 与主线程之间使用明确协议并测试错误恢复。

### 旧班表与新规则

规则保存、航班增删、人员状态变化和行政支援切换可能让当前 assignments 失效。不要让旧结果继续显示“规则已执行”；标记过期，并通过明确按钮重新生成。

## 10. 外部数据与环境路径

### 在线航班查询

`Failed to fetch` 曾来自浏览器 CORS、目标站反爬或无稳定公开 API，不是简单改 URL 就能解决。接外部数据前确认：

- 是否有允许跨域的稳定接口。
- 日期范围和机场筛选是否满足业务。
- 数据授权和登录方式。
- 失败、空结果和日期不一致时禁止自动删除当前航班。
- 查询只生成对账建议，新增和删减由用户确认。

没有可靠来源时明确停止，不把抓网页包装成稳定功能。

### 路径和多个开发服务器

项目曾从 `C:` 盘移动到 `G:` 盘，IDE 上下文仍提供旧路径；同时存在多个 Vite 端口。每次开始和交付时核对：

```powershell
git rev-parse --show-toplevel
git status --short
Get-CimInstance Win32_Process | Where-Object { $_.CommandLine -like '*vite*' }
```

不得在失效副本上修改，也不得因端口被占用就误认为最新服务已启动。

## 11. 标准修复流程

1. 用业务语言写出错误结果与正确结果。
2. 定位用户实际日期、航班、岗位、人员、模式和配置。
3. 建立最小匿名失败测试，先看到红灯。
4. 沿完整排班管线列出至少三个可证伪原因。
5. 找到最早发生错误的阶段，不在最后反馈层打补丁。
6. 对照 `spec.md` 写规则冲突表并取得授权。
7. 修改所属模块；中央管线只增加清晰的阶段调用或具名状态。
8. 运行失败测试，确认转绿。
