# 排班维护经验

仅在任务涉及排班规则、候选顺序、岗位锁定、疲劳、轮岗、人工调整或反馈时读取。产品当前事实以根目录 `spec.md` 为准；本文件记录维护方法、owner 偏好和已发现风险，不得代替产品规格。

## Owner 偏好

- 修改前先用业务例子说明理解、影响范围、不变规则和验收边界，得到确认后再写文件。
- 使用简体中文和大白话解释；术语必须能对应到具体航班、岗位、人员或日期。
- 显式顺序优先于隐式权重。禁止综合分、超大权重、姓名特例和无法解释的黑盒评分。
- 人名和航班案例只用于复现，规则必须适用于全部符合条件的人员与航班。
- 岗位完整性、重点岗位公平、疲劳恢复和反馈证据必须同时核对，不能修复一项后静默破坏另一项。
- 未实现、未验证或仅计划的内容不得写成已经完成。

## 规则变更入口

开始修改前逐项回答：

1. 规则 ID 是什么，属于硬约束、特殊锁定、岗位完整性、人员保护与公平、稳定排序还是排班后复核？
2. 它排在谁之前、谁之后？与值班、`KE166`、12点前完整性、跨工作日恢复、重点岗位频率和普通轮岗分别如何冲突？
3. 它是不可突破、优先避开，还是无人替代时允许兜底？兜底后反馈写什么证据？
4. 它会不会造成岗位空缺、0工时、工时超限、疲劳集中、重点岗位高频或旧锁定被移动？
5. 人工调整后，哪些自动决策记录必须失效或重新计算？
6. 哪个失败测试能在修改前稳定复现问题，哪些既有回归必须保持？

## 固定开发顺序

1. 完整读取 `AGENTS.md`、`spec.md`、`README.md` 和本文件。
2. 从真实入口追踪任务生成、候选过滤、逐项比较、锁定、后置重排和反馈，不用界面文字猜测算法。
3. 列出新规则与现有规则合同的冲突；规范和实现不一致时先上报，不自行统一。
4. 先写失败测试或行为等价测试，再修改实现。
5. 每条规则只进入所属职责模块；跨阶段影响通过中央管线、具名状态和显式锁定表达。
6. 检查最终排班事实、结构化决策和反馈是否一致。
7. 同步事实文档并完成类型检查、全部测试、生产构建、完整验证和差异检查。

## 高风险回归矩阵

每次规则调整至少检查受影响的项目：

- 硬约束：状态、人员类型、岗位资质、夜班、时间冲突、每日工时。
- 特殊锁定：值班早班、值班晚撤、`KE166` 机动督导及绑定兼任柜台。
- 岗位完整性：12点前稀缺岗位、跨航班抽调、同航班空缺下沉、行政支援替换。
- 人员保护：岗位衔接、高负荷、滚动负荷、跨工作日恢复、当日工时与疲劳。
- 公平轮岗：重点岗位自然月与最近6班频率、普通岗位第三次连续、三人安全重排。
- 人工路径：拖拽、交换、清空、临时岗位、机动督导同步、过期决策记录。
- 反馈：实际执行、保护突破、无法调整原因、当前事实和历史基准必须一致。

## 当前排班模块边界

- `scheduler.ts` 只保留 `generateSchedule` 中央管线，按公开阶段串联任务、候选、锁定、完整性修复、轮岗复核和最终输出。
- `schedule-tasks.ts` 负责岗位任务定义和是否自动排班；`schedule-position-rules.ts` 负责岗位显示与有效岗位事实。
- `assignment-eligibility.ts`、`assignment-timing.ts` 和 `assignment-validation.ts` 分别负责基础候选资格、时段/工时计算和人工改派校验。
- `duty-assignment.ts` 与 `ke166-assignment.ts` 负责特殊岗位锁定；`candidate-qualification.ts` 负责稀缺资质判断。
- `schedule-protection.ts`、`schedule-frequency.ts` 和 `schedule-decision-notes.ts` 分别负责保护规则计算、历史频率事实和结构化说明。
- `workload-accounting.ts` 统一定义哪些当天分配计入工时、疲劳、保护、统计和归档；行政支援岗位及行政支援人员必须在这里统一排除。
- `assignment-evidence.ts` 统一清除人工调整后已经失效的系统说明和结构化自动决策记录。
- `schedule-coverage.ts` 负责12点前缺员说明及同航班岗位空缺下沉。
- `rotation-review-safety.ts` 是轮岗重排的统一安全检查；`position-frequency-review.ts` 和 `position-rotation-review.ts` 分别处理重点岗位频率与连续轮岗，禁止互相复制安全约束。

## 已发现但未授权修复的风险

以下是只读审核结论，不代表已经修复。相关任务必须先复现并向 owner 确认行为边界：

- 某些候选预筛选会早于公开的逐项比较顺序执行，修改时必须核对真实优先级，而不能只看规则数组。
- 高负荷、滚动负荷和跨工作日恢复只有“启用/停用”一种执行语义：启用后优先避开，无安全替代时保证岗位完整。只有岗位衔接间隔规则保留“优先避开/严格限制”，不得在界面或反馈中把前三类保护描述成强限制。
- 历史导入记录没有岗位规则 ID 或岗位分类；旧文件无法反推某条记录当时是否属于行政支援岗位，只能依赖人员类型排除行政人员。新归档必须从源头排除行政支援负荷。

## 行为保持型重构

- 先冻结语义结果，再移动代码。比较航班、岗位、人员、状态、空缺、工时、疲劳、系统说明、决策记录、反馈和警告；忽略随机 ID 后必须一致。
- `scheduler.ts` 只保留中央管线和公开调度入口；按变化原因拆分硬约束、任务计划、特殊锁定、候选选择、保护规则、岗位补洞、频率重排、连续轮岗、人工校验和最终输出。
- 文件拆分期间不改变规则顺序、阈值、兜底条件、文案语义、存储版本或用户操作。
- 任何语义差异都视为重构失败；停止继续拆分，定位差异并向 owner 报告。
