# autoschedule Development

把本 skill 当作本项目的开发门禁。产品事实以根目录 `spec.md` 为准，本 skill 只规定如何可靠地理解、修改和验证项目。

## 开始前

1. 读取根目录 `AGENTS.md`、`spec.md`、`README.md`；存在当前 `plan.md` 时一并读取。
2. 检查 Git 根目录、分支、`git status --short`、全部相关未提交差异、当前真实项目路径、运行入口和验证入口。不得假设 IDE 中的旧路径仍有效。
3. 区分：已验证事实、owner 提供但未复现的现象、推测、计划和已经完成且验证的事项。
4. 涉及自动排班、规则优先级、值班、`KE166`、岗位完整性、疲劳、轮岗、人工调整或反馈时，完整读取 [排班维护经验](references/scheduling-maintenance.md)。
5. 遇到历史反复问题、规则打架、结果与规则文字不一致、补洞失败、卡死、导入丢配置或“修一处坏一处”时，完整读取 [历史顽疾与防复发手册](references/development-lessons.md)。
6. owner 要求计划时才读取计划 skill 并维护 `plan.md`；owner 明确免除时不创建。

## 修改门禁

在写文件前，用大白话向 owner 说明并取得确认：

- 用一个真实业务例子复述期望结果。
- 列出修改范围和明确不变的行为。
- 指出与现有 `spec.md`、中央规则合同、锁定、完整性、恢复和轮岗的冲突。
- 说明允许突破条件、反馈证据和验收边界。

发现新冲突或需要扩大范围时停止写入，重新确认。相互依赖的问题逐个问；独立问题一次最多 4 个。

## 证据优先

1. 从真实入口追踪 `任务生成 → 候选资格 → 预筛选 → 逐项比较 → 锁定 → 补缺 → 后置复核 → 反馈`，不要只看规则页面文字或某个排序字段。
2. 优先使用用户实际日期、航班、岗位和浏览器状态复现；把含姓名的数据匿名化后固化成最小测试。
3. 修复前先运行能稳定出现精确症状的失败测试。若没有合适测试入口，先说明架构缺口。
4. 至少提出三个可证伪原因，再用测试或检查逐项排除；不要用第一个听起来合理的解释直接改代码。

## 规则合同

任何排班规则变更先写清：

- 唯一规则 ID 与所属阶段。
- 前置规则、后置规则和固定的逐项判断顺序。
- 不可突破、优先避开或无人替代时兜底。
- 锁定的是具体岗位、人员、岗位组还是日期，不得扩大锁定语义。
- 失败时保留岗位完整性还是允许空缺，以及反馈写出的具体原因。
- 对人工调整、行政支援、`KE166`、值班和历史统计的影响。

禁止综合权重、超大权重、姓名特例、魔法数字和黑盒分数。使用具名字段、固定阶段和字典序比较；每一步只有在前一步相同时才进入下一步。

## 实现边界

- 不继续把新规则直接堆入 `src/domain/scheduler.ts`；把事实计算、候选比较、锁定、补缺、复核和反馈放入各自职责模块，由中央管线显式串联。
- 行为保持型重构与业务行为修改分开交付。重构先建立语义等价基准，不顺手调整规则。
- 锁定使用明确的 assignment ID 或岗位组，不用人员身份代替岗位锁定。
- 展示、业务事实和负荷核算分开处理；隐藏文字不得删除岗位备注等业务数据。
- 结构化配置必须覆盖默认值、状态模型、迁移、localStorage、Excel 导入导出、页面编辑和往返测试。
- 人工修改后清除失效的自动决策证据，并从最终排班事实重新生成反馈。
- 不覆盖或回滚 owner 的无关改动，不建立旧别名、兼容转发或临时过渡文件。

## 回归检查

根据风险至少覆盖：

- 硬约束：状态、人员类型、岗位资质、夜班、时间冲突、每日工时。
- 特殊边界：值班最终保留12点前上午航班且只锁晚撤岗位、`KE166` 独立机动督导及缺员时的兼任组、人工岗位。
- 岗位完整性：中间不得留洞、稀缺岗位、跨航班抽调、行政支援替换、分队长并行督导。
- 人员保护：岗位衔接、跨工作日恢复、截止时间、滚动负荷、动态疲劳互补。
- 公平轮岗：重点岗位连续与频率、普通岗位第三次连续、同航班/重叠航班/连续轮岗最多五个逻辑岗位的最短安全闭环。
- 数据边界：旧状态迁移、配置导入导出、未知或缺失工作表、人工覆盖。
- 结果证据：岗位、人员、空缺、工时、疲劳、备注、系统说明、结构化决策、反馈和警告一致。
- 性能：候选搜索有明确深度、状态去重和终止条件；大型真实夹具不会卡死或栈溢出。

## 文档与验证

- 产品事实变化时同步 `spec.md`；用户操作变化时同步 `README.md`；长期协作纪律变化时同步 `AGENTS.md` 和本 skill。
- 先运行最接近改动的测试，再依次完成：

```powershell
npm.cmd run typecheck
npm.cmd test
npm.cmd run build
npm.cmd run verify
git diff --check
git status --short
```

- 交付时说明根因、实际规则顺序、修改文件、新增回归、真实命令结果、未验证项和剩余风险。
- commit、push、部署和发布只在 owner 明确授权后执行。
- 任何未实现、未运行或未验证内容都不得写成已经完成。
