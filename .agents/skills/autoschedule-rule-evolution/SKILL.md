# Autoschedule Rule Evolution

用于持续演进排班规则的防回归门禁。它不定义具体产品规则，也不替 owner 决定冲突优先级。

## 先读

读取根目录 `AGENTS.md`、`HANDOFF.md`（若存在）、`spec.md`，以及 `autoschedule-dev` 的相关 references。定位中央规则合同、排班模型/HiGHS 输入、后置复核与 finalizer、轮岗/安全校验、导入导出和相关测试。

## 审查链路

沿真实执行路径核对并记录证据：

`输入 -> 唯一事实源 -> 候选/硬约束 -> HiGHS 模型 -> 锁定/补缺 -> 后置复核 -> 最终 assignments -> Store/页面展示`

对新增规则逐项回答：

1. 唯一规则 ID、所属阶段、拥有字段和直接消费者是什么？
2. 它是否把软目标当硬约束，或在后置阶段改回前序已满足的优先级？
3. 值班优先级、值班中间减负、末班重点岗位公平、同日 CX 重点岗位、岗位衔接和轮岗是否互相覆盖？
4. 历史归档、人工次数、Excel/localStorage 导入导出、统计和 UI 是否读写同一事实源，默认值/迁移是否闭环？
5. 最终班表是否仍满足岗位完整性、人员资格、时间冲突、疲劳和锁定规则？

## 修改门禁

- 需求、`spec.md`、中央合同、现有测试或执行阶段冲突时，停止写入，列出冲突、影响和候选决策，等待 owner 裁决。
- 先建立能稳定复现问题的失败测试；至少补一个新行为断言和一个关键旧行为不变断言。
- 规则实现放在所属 domain/规则模块；不要把特例堆进 kernel、入口或 UI，不创建第二套统计/规则副本。
- 修改后核对最小影响清单：默认值、迁移、归档、导入导出、统计、后置复核、最终 assignments、反馈和页面展示。
- 动态 import、Worker/WASM、Excel/localStorage 和最终班表证据必须显式验证，不能只依赖静态 related 测试。
- 验证按风险升级；实现改动交付前必须运行仓库要求的 `npm.cmd run verify`，并如实报告未运行或失败项目。

## 停止条件

发现第二套事实源、职责归属不清、后置复核会推翻硬约束、无法通过公共职责接口测试，或失败结果无法解释时，停止扩大修改，输出文件/函数/阶段/测试证据和下一步选项。

## 交付报告

说明已确认事实、推测、修改文件、规则执行顺序、旧行为保护、实际命令结果和剩余风险。不要把计划或未验证结果写成完成事实。
